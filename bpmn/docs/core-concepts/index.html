Core Concepts & Execution Mechanics

saccharine/bpmn translates BPMN 2.0 visual graph specifications into durable PHP coroutines. Learn how tasks execute, how state persists, and how deterministic replay guarantees stability across queue restarts.

1. Service Tasks (Automated Work)

A Service Task represents automated work performed by code without manual intervention. When a workflow token arrives at a Service Task, the engine delegates execution to a registered Activity class.

Defining an Activity Class

Activities inherit from the package base class and implement a clean, isolated execute() method: 

<?php

namespace App\Workflows\Activities;

use Workflow\Activity;
use Illuminate\Support\Facades\Http;

class VerifyFraudScoreActivity extends Activity
{
    /**
     * Executes the task.
     * Receives the current process state ($userData).
     * Returns an array of state mutations to merge back into the instance.
     */
    public function execute(array $userData): array
    {
        $response = Http::post('https://fraud-service.internal/check', [
            'email' => $userData['customer_email'],
            'amount' => $userData['order_total'],
        ]);

        return [
            'fraud_score' => $response->json('score'),
            'fraud_verified_at' => now()->toISOString(),
        ];
    }
}

Decoupled Configuration Mapping

In config/saccharine-bpmn.php, tasks declared on the visual canvas are mapped to PHP classes using task IDs or element templates: 

'activities' => [
    'verify-fraud' => \App\Workflows\Activities\VerifyFraudScoreActivity::class,
    'send-notification' => \App\Workflows\Activities\SendNotificationActivity::class,
],

When the activity finishes, its returned array merges deterministically back into the process $userData payload.

2. User Tasks (Human-in-the-Loop Hibernation)

Unlike script-based jobs that must execute to completion within standard worker timeouts, real-world business processes often pause for human intervention (approvals, form entries, or signatures).

How Hibernation Works

When an execution token arrives at a userTask node:

  1. The engine yields an awaitable signal inbox method: #[SignalMethod] submitUserTask($payload).
  2. The coroutine suspends execution immediately.
  3. The queue worker commits the current execution pointer to workflow_tokens and frees itself to pick up other application jobs.
  4. No worker processes, CPU cycles, or threads are held in memory while awaiting user action.

[Token Enters User Task]
        │
        ▼
Yields Awaitable Signal ──► Database Checkpoint Saved ──► Queue Worker Released
                                                                │
                                                                ▼
                                                        (Hours or Days Later)
                                                                │
                                                                ▼
Queue Worker Resumes ◄── Workflow Stub Woken Up ◄── Signal Received via HTTP/UI

Resuming via Signal

When an authorized user submits their review in the host application, dispatch a signal:

use Saccharine\Bpmn\Facades\Bpmn;

Bpmn::signalInstance($workflowInstanceId, 'submitUserTask', [
    'task_id' => 'manager_approval_node',
    'approved' => true,
    'reviewed_by' => auth()->id(),
]);

The durable engine locates the hibernated instance, verifies the inbox signal, and dispatches a queue job to advance the token down outgoing sequence flows.

3. Gateways & Sandboxed Expressions

Exclusive Gateways (XOR)

Exclusive Gateways evaluate conditions on outgoing sequence flows and select exactly one path.

To prevent code injection and avoid raw PHP eval(), conditions are parsed safely through Symfony ExpressionLanguage with the instance payload injected into scope: 

<!-- Example compiled sequence flow condition -->
<bpmn:sequenceFlow id="Flow_1" sourceRef="Gateway_XOR" targetRef="Task_Approval">
  <bpmn:conditionExpression xsi:type="bpmn:tFormalExpression">
    order_total >= 1000 and customer_tier in ['vip', 'enterprise']
  </bpmn:conditionExpression>
</bpmn:sequenceFlow>

If no condition evaluates to true, the engine routes through the designated default sequence flow.

Parallel Gateways (AND Splits & Joins)

When a process branches across a Parallel Gateway:

  1. The engine creates isolated child coroutine stubs for each outgoing branch.
  2. Active tokens are tracked independently across concurrent branches in workflow_tokens.
  3. At the converging join gateway, the engine executes a barrier join: 
    yield all($parallelBranchStubs);
  4. Only when all parallel branches have finished does the parent workflow resume and proceed to downstream nodes.

4. Replay Safety & Determinism

Durable coroutines operate on an event-sourcing model. When a suspended workflow wakes after an inbox signal or worker restart, the coroutine function replays from the beginning, checking off previously recorded events against its history log.

Protecting Side-Effects via WorkflowStub::sideEffect()

If an activity writes directly to an external API or database during execution, a coroutine replay could inadvertently execute those operations multiple times: 

// ❌ DANGEROUS: Re-executes multiple times during coroutine replays!
DB::table('orders')->where('id', $orderId)->update(['status' => 'processing']);

// ✅ SAFE: Wrapped in sideEffect to run once and cache during replays
WorkflowStub::sideEffect(function () use ($nodeId, $userData) {
    WorkflowHistory::create([
        'workflow_instance_id' => $this->instanceId,
        'node_id' => $nodeId,
        'payload_snapshot' => $userData,
    ]);
});

During the initial run, the closure executes and caches its return value. During subsequent replays, the engine skips closure execution and returns the cached result directly.

5. Lifecycle Controls: Suspend, Resume, and Halt

Workflows support administrative lifecycle commands via #[SignalMethod] handlers:

  • Suspend: Pauses execution at the next node barrier. The workflow yields await(fn () => !$this->isSuspended).
  • Resume: Clears the suspension flag and wakes queue workers to process pending steps.
  • Halt: Aborts the workflow instance permanently, writes a cancellation audit record, and terminates all active tokens.
